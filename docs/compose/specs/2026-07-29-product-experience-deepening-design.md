# UniBlack Product Experience Deepening Design

> [!NOTE]
> This document may not reflect the current implementation.
> See the final report for up-to-date state:
> [Final Report](../reports/product-experience-deepening.md)

## [S1] Problem

UniBlack 已具备对象、账号、事件、证据、申诉、处罚和管理闭环，近期也完成了磨砂玻璃 Shell 与基础视觉系统。当前主要差距不再是功能缺失，而是核心信息尚未形成统一、可扫描、可追溯的产品语言：公开对象与事件详情仍以通用 Panel 堆叠内容，治理队列缺少明确的处理优先级，发布页也未充分解释提交内容最终如何进入公开档案。

本轮按以下顺序深化体验：

1. 可信档案体验。
2. 治理工作台。
3. 发布引导体验。

三段共享同一套对象、事件、证据、状态和裁决语言，但分别独立验收。

## [S2] Goals

- 让访客在对象详情中快速判断“是谁、关联哪些账号、为何被记录、当前状态如何”。
- 让事件详情清晰区分事实描述、证据、可追溯信息和申诉纠错。
- 让治理人员优先看到待处理事项的上下文、理由和可执行动作。
- 让发布者理解对象账号、事件事实、证据三类信息之间的关系，并在提交前发现缺失项。
- 保留现有 API 边界、认证方式、数据模型和磨砂玻璃视觉基础，避免为体验改造引入无必要依赖。
- 在 375px、768px 和 1280px 宽度保持可用，遵守键盘焦点和 reduced-motion 约束。

## [S3] Non-Goals

- 不实现 OAuth、暗色模式、OpenAPI 或公共 API Key。
- 不移除 Sunset 之前的 Case/Submission 兼容路径。
- 不引入多页发布向导、草稿持久化、全局状态库或查询缓存库。
- 不增加批量裁决等高风险治理能力。
- 不重做全站设计系统；只添加三段体验实际复用的最小展示模式。
- 不伪造后端没有提供的证据时间、哈希、提交者或审核者信息。

## [S4] Shared Information Language

三段体验使用一致的名词和视觉顺序：

- `Subject` 是被核验的对象，以显示名和 `UBS_<ULID>` 作为档案身份。
- `Account` 是对象在具体平台上的账号；旧 Identifier 只作为兼容数据并入同一展示区，不强化旧术语。
- `Event` 是公开记录单元，必须同时表达标题、状态、严重程度和事实摘要。
- `Evidence` 是支撑事件的材料，按文本、链接、文件等真实类型展示。
- `Appeal` 是纠错路径，状态和 outcome 必须使用面向用户的中文标签，并保留原始枚举的确定映射。
- 风险、状态、严重程度不能只靠颜色表达，必须同时有文本或刻度。

共享模式保持轻量：优先在页面内组合现有 `Badge`、`Panel`、`Alert` 和状态组件；只有第二处真实复用出现时才提取新组件。

## [S5] Trustworthy Profile Experience

对象详情采用“档案”而非“卡片集合”的信息层级：

1. 档案抬头：显示对象名、公开 ID、记录状态、风险等级和简短解释。
2. 账号簇：按 Account 优先、Identifier 兼容的顺序列出平台和值；第一条账号作为主标识，但不推断后端未标记的真实性。
3. 公开事件轨迹：使用纵向关系线或清晰分隔呈现事件顺序；每项显示标题、状态、严重程度、摘要和查看证据入口。
4. 无事件时明确说明当前没有公开事件，而不是暗示对象绝对安全。

事件详情分为四层：

1. 事件抬头：标题、状态、严重程度和事件 ID。
2. 事实描述：保留换行，明确这是社区公开记录。
3. 证据清单：按真实类型展示标题、描述和链接；缺少证据时显示克制的空状态。
4. 纠错区：申诉入口、申诉历史和 outcome，使用中文状态语言并说明可用条件。

页面继续使用现有公开 API。若响应中没有 Subject 反向链接，不为事件页伪造对象链接。

## [S6] Governance Workbench

管理端保持现有侧栏和 RBAC 守卫，重点优化队列页内部的信息密度：

- 页面抬头同时表达任务名称、当前待办数量和简短处理原则。
- 过滤与刷新操作集中在紧凑工具区，移动端可自然换行。
- 申诉条目优先展示事件标题或 ID、申诉状态、用户理由、已有裁决和处理动作。
- 枚举状态统一映射为中文标签；必要时在辅助文本保留原始值以便审计。
- 危险或不可逆动作继续逐项确认；不新增批量裁决。
- loading、empty、error 和 unauthorized 继续使用共享状态组件。

其他管理页只在其模式能直接复用且不扩大范围时采用同一队列抬头或工具区，不进行全后台重写。

## [S7] Guided Publishing

`/submit` 保留单页和现有 multipart 发布协议，改为三段任务流：

1. 对象账号：解释对象显示名由首个账号解析，要求至少一个有效账号。
2. 事件事实：填写标题、详情、严重程度等现有字段，强调可核验、克制描述。
3. 证据与确认：组织文本、链接和文件证据，显示提交前检查与验证码/认证要求。

每段包含稳定编号、标题、简短说明和完成状态。完成状态仅由当前表单值计算，不新增持久化。字段错误在对应分区附近显示；提交失败保留全部输入，并将页面焦点或可见错误提示引向失败分区。成功后沿用现有跳转或成功反馈，不改变 API 行为。

## [S8] Data Flow And Boundaries

- 页面继续通过 `lib/api.ts` 调用 API，不直接读取 token、拼接 Authorization 或自行处理 401。
- 现有 `lib/types.ts` 是前端领域类型真源；仅在 API 已返回但类型缺失时补充字段。
- 页面展示逻辑使用纯函数或局部映射时，优先在同文件内实现；出现第二个消费者后再提取。
- 不修改数据库迁移或后端模型，除非实施调研证明批准的体验无法使用现有响应表达。任何后端补充必须是只读响应字段或既有关系的最小暴露，并单独测试。
- Case/Identifier 兼容数据继续可读，但新文案使用 Subject/Account/Event 语言。

## [S9] Error Handling And Accessibility

- 所有异步页面具备 loading、empty、error 和 normal 状态；受保护页面继续依赖既有 unauthorized 守卫。
- API 错误显示可恢复信息，不清空用户已输入的发布或申诉内容。
- 外部证据链接使用新窗口和 `rel="noreferrer"`；文件若没有可访问 URL，不渲染无效操作。
- 状态、风险和严重程度同时使用文本与视觉标记。
- 标题层级、列表语义、表单 label 和 focus-visible 保持完整。
- 所有新增过渡限制在状态反馈范围内，并受 `prefers-reduced-motion` 控制。

## [S10] Testing And Acceptance

每段实施均需：

- 为新增的纯状态映射、完成度或交互逻辑补充 Vitest，避免只测试静态 className。
- 扩展 Playwright 覆盖对应关键路径，并至少包含桌面与移动视口中的可见性和主要操作。
- 运行 `npm run test:run`、`npm run lint`、`npm run typecheck`、`npm run build`。

最终验收增加：

- 公开对象档案可看到身份、账号、风险状态和事件入口。
- 公开事件页可区分事实、证据与申诉纠错，空证据状态不误导。
- 管理员可以扫描申诉队列并完成现有单项裁决流程。
- 发布者可以识别三段完成状态，错误不会清空输入。
- 完整 Playwright 套件通过；375px、768px、1280px 无关键内容溢出。
- `docs/frontend-gap-analysis.md` 更新状态与验证证据。

## [S11] Delivery Strategy

实施采用共享语言先行、三段依次合入：

1. 可信档案：对象详情、事件详情及其测试。
2. 治理工作台：申诉队列优先，复用第一段状态语言。
3. 发布引导：利用前两段已稳定的信息结构重排表单。

只读调研、测试设计和独立评审可以由子进程并行进行；页面实现按上述顺序整合，避免同时修改共享 UI 和类型造成冲突。每一段完成验证后再进入下一段，最终统一运行完整验证。

## [S12] Decision Trace

- 选择“可信档案 → 治理工作台 → 发布引导”，因为它从公开价值出发，再统一内部治理，最后反向约束数据入口。
- 选择分段深化而非三线同时实现，因为共享状态语言和组件边界需要先稳定；并行只用于独立调研与评审。
- 保留现有 API 和单页发布，因为当前功能闭环已经完成，本轮目标是信息架构和任务效率，不是协议重构。
- 不做全站设计系统扩建，因为只有出现真实复用时才应抽象，符合最小实现原则。
